# AI candidate lifecycle — Phase 4C.1 design

Proposed contract for owner review. The code baseline is merged `main` at `396f14a6de9f839e63dbe943ed2b9f77d78c0243` (Phase 4B.2), verified against the remote. The design file is in the supplied feature workspace.

## 1. Problem and MVP journey

AI assistance currently returns temporary suggestions. An evaluator generates suggestions in Findings, inspects the cited observations and uncertainty, and explicitly saves an eligible suggestion. An authorized reviewer opens the saved candidate, checks the original evidence, and records **accepted for consideration**, **rejected**, or **more evidence required**. Acceptance applies only to the candidate. Phase 4C.4 introduces a separate human action that creates a new `proposed` finding using the existing Finding model and review workflow. Corrective actions remain in their existing human workflow. Deterministic analysis remains authoritative.

Reuse the Findings tab, its AI panel, and the existing citation and review controls. Put **Save candidate** on eligible suggestion cards and a **Saved candidates** queue beside the AI panel, with pending review and more-evidence states easy to find. In the detail view, show source wording, filename and locator first, followed by counterevidence, interpretation, uncertainty, and decision history. Use explicit action labels such as **Accept for consideration**. Show stale status and its reason alongside the last human decision. Label historical quotations when the original can no longer be opened. Keep the queue visible to authorized users when generation is disabled and exclude candidates from finding counts and reports.

The merged code provides reusable `AiResult`/`Suggestion`, scoped `read_context`, citation and advisory validation in `backend/app/ai_evaluation.py`; `Source`, `Observation`, `Exercise`, `Finding`, `CorrectiveAction`, `ExerciseGrant`, and `AuditEvent` in `backend/app/models.py`; `_exercise_for_user`, `_audit`, existing review endpoints and role sets in `backend/app/main.py`; and the Findings view, `AiAssistance.tsx`, citation links, and review UI patterns. Current objectives are entries in `Exercise.objectives_json`, not rows with foreign keys. Existing AI generation is `POST /api/exercises/{exercise_id}/ai-suggestions`, restricted to admin/evaluator; output is not persisted. Existing finding review is admin/reviewer and accepts a single decision on a proposed finding. The two existing Alembic revisions end at `a53481bc2d73`; extend that chain in a later phase.

## 2. Lifecycle

Review state and evidence freshness are **separate**: a stale candidate retains its human decision and history. The model never sets either state or invokes transitions.

| Current review state | Human transition | Next state | Conditions |
| --- | --- | --- | --- |
| New explicit save | save | `pending_review` | Valid, current, source-linked server-issued suggestion; reviewer decision null. |
| `pending_review` | accept / reject / request evidence | `accepted_for_consideration` / `rejected` / `more_evidence_required` | Authorized reviewer; current version and current evidence. |
| `more_evidence_required` | accept / reject | `accepted_for_consideration` / `rejected` | Authorized reviewer; current version and current evidence. Record the reason when requesting evidence. New evidence creates a new candidate, not an edit to the old one. |
| `accepted_for_consideration` | request evidence / reject | `more_evidence_required` / `rejected` | Authorized reviewer; current version and current evidence; retain all earlier decisions. |
| `rejected` | none | `rejected` | Terminal. It is retained with its history. |

Freshness is stored as `current` or `stale` with machine-readable reasons. A confirmed mismatch makes any review state stale permanently. The history and last decision remain visible, and the candidate is read-only. Generate and explicitly save a new candidate against new evidence. The server records invalidation. In 4C.4, a single finding link records promotion and closes further candidate review. The linked finding enters the existing human review workflow as `proposed`.

## 3. Data and provenance contract

One candidate is an immutable generation-time evidence snapshot plus mutable workflow metadata. Use an explicit, versioned schema and constraints, not unstructured model output. At minimum:

- **Identity and scope** include candidate ID, exercise foreign key, and objective ID. Preserve the bounded objective text and the fingerprint of its definition, including the evaluation rule, so a reviewer can identify the original target after an edit. Validate objective existence and uniqueness in the exercise JSON. Derive the candidate's organization from the exercise's authoritative, immutable organization binding.
- **Immutable suggestion:** server-rendered `interpretation`, relationship `kind` (`relevant_observation`, `corroboration`, `contradiction`, `different_response_phases`, `unknown`, or `insufficient_evidence`), `assessment` (`advisory` or `abstained`), `unknowns`, `uncertainty`, and review reason. “Validated” means source and rule checks passed, not that the interpretation is correct. Preserve counterevidence separately from support. Require at least one usable source citation for a saved candidate; a citation-free abstention remains ephemeral with an explanation.
- **Immutable citation snapshot:** for each supporting and counterevidence observation, source ID, observation ID, filename, precise locator, complete observation wording as returned by the validator, source SHA-256, and a fingerprint of the observation text and provenance. Retain extraction method, recognition confidence when available, raw reported event time, time-confidence and transcript segment/offset or OCR page provenance when available. A transcript offset is not an event time; OCR time and wording require original-page verification. References and the minimum quotation snapshot preserve historical meaning even if live data changes; they are not document copies. All citations must belong to the same exercise and resolve to live scoped records at save.
- **Immutable generation provenance:** provider, exact model identifier, verified model digest when available (`null` otherwise), prompt version, output/validator schema version, generation time, authenticated requesting user ID, and a versioned generation-context fingerprint. Never infer a digest from a model tag. No raw prompt, credentials, full document copies, or unnecessary personal data are retained. Candidate text may itself contain sensitive source material; apply the existing exercise access, backup, and retention controls.
- **Mutable workflow** includes review state, freshness, first detected stale time and reason(s), integer version starting at 1, and updated time. Derive the latest human decision, reviewer user ID, note, time, and event IDs from existing audit events ordered by candidate version. The candidate response returns `reviewer_decision: null` until a human decision exists. In 4C.4, the new finding uses the existing `Finding.status = "proposed"` and `Finding.reviewer = null` convention. Keep missing ownership, cause, event time, and deadlines unknown.

Content, scope, source snapshots, generation provenance, and original fingerprints never change after creation. Every workflow mutation uses a version-checked transaction and appends an audit event. Retain historical quotations and events under the exercise's existing protection; do not promise indefinite retention independently of the owner's future deletion policy.

## 4. Authorization

Every operation authenticates the current configured identity, checks its current role, and requires both matching exercise ownership and a live `ExerciseGrant` for that user and organization. Candidate lookups are scoped to the authorized exercise before returning anything. Cross-exercise and cross-organization IDs return 404 without disclosing existence. An authenticated user with insufficient role receives 403. Revoked or deactivated identities lose access on the next request. Existing CSRF and session protections apply to writes.

| Operation | Admin | Evaluator | Reviewer | Viewer |
| --- | --- | --- | --- | --- |
| View queue, candidate, citations and history | yes | yes | yes | yes |
| Generate suggestions | yes | yes | no | no |
| Explicitly save own generated suggestion | yes | yes | no | no |
| Accept, reject, request more evidence | yes | no | yes | no |
| Future explicit promotion to proposed finding | yes | no | yes | no |

All “yes” entries require the matching exercise grant and organization. Promotion is a review-authorized operation, even though ordinary proposed-finding edits use editor roles. A request cannot supply its own actor, decision timestamp, organization, or review state.

**Organization prerequisite.** Add an immutable `Exercise.organization_id` during 4C.2. The current grant rows are a source for backfill but can disappear on revocation. Recommend backfill only when all retained grants agree on one nonempty organization. Preflight must report zero-grant and conflicting-grant cases for explicit owner resolution before enforcing the constraint. Apply the binding across exercise creation, listing, lookup and grant changes, and cover both startup and interactive demo seeding. Assign new exercises from the authenticated creator and startup demo ownership from the configured demo owner. Existing exercise IDs stay globally unique.

## 5. Proposed API contract

All endpoints are exercise-scoped, authenticated, no-store and use existing error conventions. They are proposals, not present endpoints.

- Extend `POST /api/exercises/{exercise_id}/ai-suggestions` to return a short-lived, server-signed save token on each eligible suggestion. Generation makes no candidate or audit writes. Bind the token to the issuer, organization, exercise, objective, unique issuance ID, accepted suggestion fingerprint, context fingerprint, generation provenance, expiry, and the bounded, parsed model entries for that objective needed to rerun validation and suggestion selection. Keep the raw provider reply and prompt out of the token and database. Sign with a purpose-specific key derived from configured secret material. The signed data is readable by its holder, so protect it like source evidence and exclude it from logs. Expired or unverifiable tokens require regeneration unless the request is a committed replay.
- `POST /api/exercises/{exercise_id}/ai-candidates` accepts `save_token` and requires `Idempotency-Key`. For a new save, authorize the caller, verify the token, reload scoped context and original-source availability, rerun validation without a provider call, and compare the resulting suggestion fingerprint with the signed value. Insert the candidate and save event atomically. Return 201 with candidate ID and version. If validation fails, return the relevant error without saving a partial candidate. Permit the new request headers and expose `ETag` in the existing CORS configuration where applicable.
- `GET /api/exercises/{exercise_id}/ai-candidates` returns a paginated queue of summaries. `GET /api/exercises/{exercise_id}/ai-candidates/{candidate_id}` returns full citations, current freshness, latest decision, and audit-derived history. Revalidate before reporting a candidate current. Return the detail version in `ETag` as a quoted integer.
- `POST /api/exercises/{exercise_id}/ai-candidates/{candidate_id}/review` accepts `decision` from `accepted_for_consideration`, `rejected`, or `more_evidence_required` and an optional `note` of at most 3,000 characters. Require a nonblank note for `more_evidence_required`. Require `If-Match` with the quoted version and `Idempotency-Key`. Check transition, authorization and freshness in one transaction and return the committed decision and version.
- **4C.4 only:** `POST /api/exercises/{exercise_id}/ai-candidates/{candidate_id}/promote`, requiring version and idempotency key, creates one linked `proposed` finding after explicit human review and revalidation. Inputs, mapping, and evidence must satisfy existing finding constraints; unsupported or ambiguous content cannot be converted into an asserted finding. No action is created. Return the existing linked finding on a valid retry.

Use 401 for absent authentication, 403 for role failure, 404 for unavailable scope, 422 for malformed/invalid suggestion, 409 for changed evidence, illegal transition or conflicting idempotency key, and 412 for an `If-Match` mismatch; indicate a missing precondition explicitly (428). Preserve existing AI-disabled and provider failure codes. Responses never expose cross-scope data.

## 6. Staleness, concurrency and recovery

Compute a versioned canonical fingerprint over the complete exercise-scoped AI context used by validation: objective definitions and rules, ordered source/observation identities, source fingerprints, full observation text and locator, extraction and timing provenance, and relevant validation/context version. This is deliberately conservative: adding or changing evidence may alter counterevidence or the relationship even when quoted text is unchanged. Store per-citation fingerprints for diagnosis. Hash canonical structured values with explicit schema/version and unambiguous serialization; do not hash only filenames or the original file bytes, since OCR corrections can change extracted text without changing bytes.

- A change to a source, observation, OCR wording or provenance, objective, validation context, or validator version makes the candidate stale. Compare fingerprints for supporting and opposing evidence. A missing original also makes the candidate stale. The current download endpoint can return extracted text when original bytes are absent, so a successful download alone does not establish original availability. Objective edits still invalidate candidates because AI can run before deterministic analysis locks the objectives.
- Recheck candidate list and detail reads and immediately before review or promotion. Check existing source and objective mutation paths as well. The first confirmed mismatch atomically marks stale, increments version, and appends one system audit event with reason and detection time. Use codes such as `objective_changed`, `source_unavailable`, `citation_invalid`, `context_changed` and `validator_changed`. A mutation request that detects a mismatch commits the invalidation before returning a conflict for the requested decision. For a verification outage where validity cannot be determined, return 503 and retry safely. This differs from a confirmed missing source, which makes the candidate stale. Preserve all prior events and decisions.
- A model becoming old, being removed, or a newer model becoming available alone does not invalidate an unchanged candidate. Show its generation model/digest and date; any policy-based model invalidation must be explicit and audited. AI disabled or a provider outage does not hide saved candidates or prevent source-based human review, but blocks generation and saving of newly issued suggestions while disabled. No model call is needed for freshness verification.
- The current API has no exercise deletion endpoint. Until an exercise-wide retention policy is agreed, protect candidate and audit history with restrictive exercise references and verify enforcement on both supported databases. Source retention and deletion paths must preserve the historical citation snapshot and invalidate affected candidates.
- Use an atomic compare-and-swap on candidate version and state, plus transactional evidence/context consistency and an audit insert. A concurrent source mutation must not race a successful save/review/promotion: lock or otherwise serialize the shared exercise context and candidate, using a tested equivalent for PostgreSQL and SQLite. Only one competing review wins; the loser receives 412, reloads, and deliberately decides again. Atomic rollback leaves neither partial decision nor orphan audit event.
- Scope idempotency to organization, exercise, actor, endpoint and key. Persist the request hash and a minimal outcome with the affected ID and applied version in the same transaction. After current authorization, return a committed exact retry before checking token expiry or current version. Return 409 for a different request using the same key. Replay describes the original write. Use a fresh detail read to show current freshness. Enforce a unique issuance ID so saving the same valid token with different keys returns the existing candidate without another audit event. Treat independently generated suggestions as separate candidates. Generation retries may invoke the model again.

## 7. Audit, integrity and model-output safety

Reuse `AuditEvent` and `_audit` in the same transaction as each save, review, invalidation and future promotion. Record action, candidate ID, exercise, stable authenticated user ID (or explicit system actor), display name as a snapshot if useful, timestamp, prior/new state or freshness, candidate version, bounded review note or reason code, and linked finding ID for promotion. Current `actor` is a display string; add stable identity in the existing event's structured details or a compatible extension, never rely on names as identity. History is append-only through application operations; events and candidate scope remain access-controlled. Failed requests do not produce misleading success events. No raw model prompt, secret, or entire document belongs in audit details.

Keep the Phase 4B.2 safeguards. AI is disabled by default, optional and available offline through the local provider. Model output is data under a strict schema. It has no tools or authority over findings, actions or lifecycle decisions. Require an exact excerpt match, then display and store the **complete observation up to 360 characters**. Withhold the result if the observation exceeds that limit, even when the excerpt matches. Withhold save eligibility if a citation fails, the context is limited, or the validator omits records when merging competing suggestions to fit the citation limit. Preserve the final server-rendered classification, documentation gaps, counterevidence and OCR uncertainty. A valid citation only shows that wording matches a scoped observation. The reviewer verifies original source context, event identity, relationship and interpretation.

## 8. Acceptance criteria for later implementation

Functional tests use isolated disposable databases and a fake provider with controlled output; they demonstrate contract enforcement, not real-model quality.

1. A granted editor explicitly saves a server-issued, source-linked suggestion. Exactly one `pending_review` candidate and one save event persist with the complete immutable snapshot, provenance, null human decision and version 1. Generation and viewing a suggestion create no candidate or save event.
2. Fabricated, out-of-scope, tampered, too-short/nonmatching, duplicate, or cross-exercise citations fail validation and create no candidate. A forged or expired save token fails; the server never trusts client-supplied text or model metadata.
3. A model excerpt of “handoff entry was found in the notebook” from the fictional record “No matching handoff entry was found in the notebook” preserves the complete negation and the missing documentation. It must never be stored as confirmation that handoff happened or failed. Verify the same preservation for a qualification in the next sentence, exactly 360 characters, and one character beyond the limit. A merged result that omitted any cited observation has no save token.
4. Exercise grant, current role, organization binding, CSRF, revocation and deactivation are enforced server-side for every endpoint, including retries and direct candidate IDs. Users from another organization or exercise cannot read, save, review, or promote even with a known ID/token.
5. Evidence, objectives, candidate IDs, and audit histories never cross exercises; a same-named objective/source in another exercise is insufficient. Ambiguous legacy organization ownership blocks migration/writes pending resolution.
6. Default-disabled AI blocks generation and new saves without modifying deterministic state; saved candidates remain readable and reviewable. No disabled-state request invokes the provider.
7. Same issuance saved repeatedly, including with different keys and concurrently, yields one candidate/event. A same-key retry returns the original outcome; altered payload conflicts. Independently generated lookalikes are not silently merged.
8. Two reviewers use the same version. Exactly one succeeds and the other receives 412. A retry with the winning key returns the same outcome. An injected audit-write failure rolls back the human decision.
9. Change or remove a cited source, original bytes, observation, OCR wording or provenance, objective or other validation context. The next read or transition detects staleness, records one invalidation event and blocks review or promotion. Test evidence added after save, evidence changed concurrently with a decision, and a transient verification outage that returns 503 without erasing history. Test that a model upgrade alone leaves a valid candidate current and that exercise deletion is blocked while history exists.
10. Authorized accept, reject and request-evidence transitions follow the table; required note, state/version checks, terminal rejection and stale restrictions are enforced. Acceptance does not create or approve a finding; rejection does not erase history.
11. Save, every successful human decision, invalidation and later promotion have ordered, attributable, append-only audit events, stable actor identity, timestamps and before/after state. Rollback, retries and conflicts do not duplicate success events.
12. Fake model output cannot set review state, reviewer, timestamps, promotion, finding status, actions or execute tools. Only an authenticated authorized human request can cause a human transition.
13. Promotion is unavailable before 4C.4. It then requires an accepted and current candidate, human authorization and revalidation. It creates at most one `proposed` finding with `reviewer = null` and no corrective action. The existing finding review is the only way to record finding approval. A second promotion cannot create another finding, including with a different request key.
14. Snapshot deterministic assessments, findings, action records and decisions before generation, save, candidate decisions, failures and restart; they remain unchanged. An explicit future promotion adds only the separately proposed finding and its evidence link/audit.
15. OCR-sourced citations retain page, method, reported time and uncertainty; uncertain times do not become verified event times or reliable elapsed-time conclusions. Transcript offsets remain locators. Missing/conflicting facts remain unknown.
16. Timeout, unavailable/misconfigured provider, invalid JSON/schema, model errors, oversized input/output and context limits produce clear bounded failures/abstentions, no candidate or partial audit, and leave deterministic workflows available.
17. Restart against the same test database and configured secrets: saved candidates, version, citation snapshots, decisions, idempotency outcomes and audit history recover intact. Exercise migration upgrade and recovery on supported SQLite and PostgreSQL; never use an existing user database for destructive testing.
18. **Fictional panel regression.** For `PANEL-STAGES`, “the operator isolated Panel D for testing” (control line 1) and “I saw Panel D returned to service after testing” (observer line 1) are different QC-7 response stages. Preserve `different_response_phases` and both observations. For `PANEL-ID`, “I saw Panel D released but did not write down the exercise run or receiving team” (observer line 2) cannot resolve the two plausible matches (control lines 2 and 3). Preserve `unknown` or `insufficient_evidence`, `event_identity` uncertainty, and the relevant original records. Fake-provider tests verify that both safe results survive save and review. Also inject a wrong but citation-valid relationship to verify that the UI presents it as advisory and a reviewer can reject it. Real-model quality testing scores stage separation and abstention separately and reports either misclassification as a miss. [Fictional panel fixture and labels at the merged baseline](https://github.com/deepeshaiml/DrillLoop/blob/396f14a6de9f839e63dbe943ed2b9f77d78c0243/evals/phase4b1/confirmation/cases.json#L84-L158)

For real-model evaluation use independently reviewed source-level labels where available; distinguish citation validity, event identity, relationship correctness, abstention and OCR timing. Existing Phase 4B/4B.1/4B.2 fixtures and labels are fictional and developer-authored, not independently adjudicated; the confirmation set records the panel-stage and identity misses. These fixtures cannot establish operational accuracy or a pass on future model outputs. Report model, digest if available, settings, dataset version, failures and label limitations; do not substitute fake-provider results for a quality evaluation.

## 10. Open owner decisions

1. Confirm exercise-organization ownership and remediation of existing exercises with missing or conflicting grants before migration; decide who adjudicates ambiguous records.
2. Confirm exercise-wide retention and eventual deletion policy for source snapshots, candidate decisions and audit events; deletion remains blocked until resolved.
3. Confirm whether reviewers may reverse an acceptance to reject or request more evidence as proposed, and whether rejection should remain terminal.
4. The implemented Phase 4C.4 policy below governs the initial mapping. A separate owner decision is needed before supporting neutral findings about evidence discrepancies.
5. Set operational token lifetime, key rotation and idempotency-record retention; retain retry guarantees for the stated retention window and disclose expiration. Decide whether citation-bearing abstentions should be saveable; this proposal permits them while citation-free abstentions remain temporary.
6. Choose whether optional reviewer notes require additional retention/privacy limits and whether independently adjudicated evaluation labels can be supplied. No quality claim depends on that choice.

## 11. Implemented Phase 4C.4 promotion policy

Candidate acceptance records a decision on the advisory record. A granted reviewer or administrator uses **Create proposed finding** to enter a title, an evidence-based observation and an interpretation, select strength or improvement, and explicitly confirm the retained objective and wording against the original evidence. The finding starts proposed with an unassigned reviewer and empty review note. The ordinary finding review records approval or rejection separately.

Only current, accepted `relevant_observation` or `corroboration` candidates with at least one valid supporting citation qualify. Candidates with counterevidence, unresolved event identity or cause, contradictions, different response phases, or abstentions remain available in candidate review. A documentation-gap source can support bounded wording about what the record contains. Reviewers check the whole observation and leave uncertain timing and causality unresolved unless the source establishes them. Free-text interpretations depend on human judgment. An exact source match establishes quotation and provenance integrity.

The exercise write lock serializes promotion with review, evidence ingestion, grant changes and deterministic analysis. PostgreSQL locks the exercise row and SQLite uses a reserved write transaction. The server reloads the complete validation context, compares the objective and evidence fingerprints, checks cited originals, and compares each saved citation with the current scoped observation and provenance. Promotion uses the same source-eligibility check as finding approval. A confirmed mismatch records candidate invalidation and an unavailable verifier returns a retryable error.

For one objective, the server blocks promotion when a supporting observation ID is already cited by an existing finding, including findings in historical states, or by a current rule result that can produce a finding. A known rule conflict that involves the candidate's evidence keeps that candidate in review, even if the advisory response cited only one side. If new evidence later makes a rule draft share support with an existing promotion, analysis still returns the assessment for review and skips writing the overlapping finding or action. Matching wording can describe different events. Reviewers still reconcile reports of the same event from different observation IDs.

Revision `73fd42ec9075` adds a one-to-one association with restrictive composite foreign keys on both SQLite and PostgreSQL. The association protects the finding from deterministic updates and staleness cleanup and supplies the candidate link to the UI and PDF export. The finding uses its UUID to generate the `AI-` code. A promotion advances the candidate version and closes its review transitions. The versioned audit event retains the authenticated promoter and finding ID. Finding creation, linkage, audit and idempotency outcome commit together. The link retains access to the generation and evidence snapshot, including OCR metadata and transcript locators. No new application dependency or model is required for this phase.
